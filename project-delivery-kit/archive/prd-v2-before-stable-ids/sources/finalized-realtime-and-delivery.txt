For the MVP, use Socket.IO rooms scoped to restaurant:{id} and booking:{id}. All subscriptions must be authorized. Events should carry a monotonically increasing booking version or sequence so reconnecting clients can detect missed updates and refresh state.

Use the transactional outbox pattern to avoid losing notifications after a successful database commit.
8. Manual and automatic table recommendation
Both selection methods must use the same inventory engine.
Feature	Manual selection	Automatic recommendation
Table choice	Customer chooses	Backend ranks candidates
Floor plan	Required	Optional
Capacity validation	Required	Required
Availability check	Required	Required
Atomic hold	Required	Required
Payment flow	Same	Same
Double-booking protection	Same	Same

For automatic selection, start with a deterministic scoring algorithm rather than machine learning.

A reasonable initial scoring model is:
\[
S=0.40C+0.25P+0.20L+0.15O
\]

Where each component is normalized to 0–100:
- \(C\): Capacity fit
- \(P\): Customer preference match
- \(L\): Seating location suitability
- \(O\): Restaurant operational efficiency
These weights are initial design assumptions, not experimentally validated values.

The recommendation API should return ranked candidates, but the actual allocation must occur through the same atomic hold operation. If the highest-ranked table becomes unavailable, the server can retry the next eligible candidate under a bounded retry policy.

12. CEO/CFO review — Is this commercially viable?
The architecture is suitable for a controlled MVP. The business model is not yet validated.
Dimension	Advantage	Risk
Manual + automatic selection	More customer choice	Restaurants must maintain accurate floor plans
Free + deposit booking	Supports different restaurant policies	Payment and refund complexity
Dine-owned inventory	Strong internal consistency	External reservations can create operational conflicts
Modular monolith	Lower initial infrastructure overhead	Requires disciplined module boundaries
Real-time tracking	Better customer visibility	More engineering and support cost

The biggest commercial weakness is restaurant adoption. Even a technically flawless booking engine has limited value if restaurants refuse to maintain inventory or customers prefer walking in.

Before building advanced recommendations, validate with 3–5 restaurants whether they actually need exact table selection, how they handle no-shows, and whether they would pay for the software.
Final engineering decisions
The following are now approved for the MVP architecture:
- Modular monolith, not microservices.
- PostgreSQL exclusion constraints and transactional row locking, not Redis-only locking.
- One inventory claim per exclusive table/time interval.
- Free and deposit reservations, controlled by restaurant policy.
- Separate payment and booking state machines.
- Outbox-backed real-time updates.
- Manual and automatic selection using one shared booking engine.
One policy still requires a product decision before implementation: Should a customer be allowed to book multiple tables for one reservation? The current design deliberately supports one table per booking. Multiple-table bookings would require atomic acquisition of several inventory claims and different capacity-allocation rules.

For the first implementation milestone, build the database migrations, transactional inventory service, hold API and concurrency tests. Do not begin with Razorpay or the mobile floor-plan animation. The reservation engine is the foundation on which everything else depends.
