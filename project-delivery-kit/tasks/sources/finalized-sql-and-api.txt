3.2 SQL schema — core booking engine
The following is a PostgreSQL 16+ migration baseline for the reservation-critical tables. It assumes authentication, restaurant onboarding and authorization are implemented in separate migrations.

CREATE EXTENSION IF NOT EXISTS pgcrypto;
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  phone VARCHAR(20) NOT NULL UNIQUE,
  name VARCHAR(120),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE restaurants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(200) NOT NULL,
  timezone VARCHAR(80) NOT NULL DEFAULT 'Asia/Kolkata',
  status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE'
    CHECK (status IN ('ACTIVE','SUSPENDED')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE floor_plans (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  restaurant_id UUID NOT NULL REFERENCES restaurants(id),
  version INTEGER NOT NULL DEFAULT 1,
  name VARCHAR(100) NOT NULL,
  is_active BOOLEAN NOT NULL DEFAULT false,
  UNIQUE (id, restaurant_id)
);

CREATE UNIQUE INDEX one_active_floor_plan
ON floor_plans (restaurant_id)
WHERE is_active = true;

CREATE TABLE restaurant_tables (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  restaurant_id UUID NOT NULL REFERENCES restaurants(id),
  floor_plan_id UUID NOT NULL,
  label VARCHAR(30) NOT NULL,
  min_capacity INTEGER NOT NULL DEFAULT 1,
  max_capacity INTEGER NOT NULL,
  x_position NUMERIC(8,3) NOT NULL DEFAULT 0,
  y_position NUMERIC(8,3) NOT NULL DEFAULT 0,
  operational_status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE'
    CHECK (operational_status IN ('ACTIVE','INACTIVE')),
  CHECK (min_capacity > 0),
  CHECK (max_capacity >= min_capacity),
  UNIQUE (id, restaurant_id),
  UNIQUE (restaurant_id, label),
  FOREIGN KEY (floor_plan_id, restaurant_id)
    REFERENCES floor_plans(id, restaurant_id)
);

CREATE TABLE booking_policies (
  restaurant_id UUID PRIMARY KEY REFERENCES restaurants(id),
  payment_mode VARCHAR(20) NOT NULL DEFAULT 'FREE'
    CHECK (payment_mode IN ('FREE','DEPOSIT')),
  deposit_amount_paise BIGINT NOT NULL DEFAULT 0,
  hold_seconds INTEGER NOT NULL DEFAULT 120,
  duration_minutes INTEGER NOT NULL DEFAULT 90,
  buffer_minutes INTEGER NOT NULL DEFAULT 15,
  CHECK (deposit_amount_paise >= 0),
  CHECK (hold_seconds BETWEEN 30 AND 900),
  CHECK (duration_minutes > 0),
  CHECK (buffer_minutes >= 0),
  CHECK (
    payment_mode <> 'DEPOSIT'
    OR deposit_amount_paise > 0
  )
);

CREATE TABLE inventory_claims (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  restaurant_id UUID NOT NULL,
  table_id UUID NOT NULL,
  starts_at TIMESTAMPTZ NOT NULL,
  ends_at TIMESTAMPTZ NOT NULL,
  state VARCHAR(20) NOT NULL
    CHECK (state IN (
      'HELD','RESERVED','BLOCKED','RELEASED'
    )),
  expires_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CHECK (ends_at > starts_at),
  CHECK (state <> 'HELD' OR expires_at IS NOT NULL),
  UNIQUE (id, restaurant_id, table_id),
  FOREIGN KEY (table_id, restaurant_id)
    REFERENCES restaurant_tables(id, restaurant_id)
);

ALTER TABLE inventory_claims
ADD CONSTRAINT no_overlapping_active_claims
EXCLUDE USING gist (
  table_id WITH =,
  tstzrange(starts_at, ends_at, '[)') WITH &&
)
WHERE (state IN ('HELD','RESERVED','BLOCKED'));

CREATE TABLE reservation_holds (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  claim_id UUID NOT NULL UNIQUE,
  restaurant_id UUID NOT NULL,
  table_id UUID NOT NULL,
  user_id UUID NOT NULL REFERENCES users(id),
  party_size INTEGER NOT NULL CHECK (party_size > 0),
  expires_at TIMESTAMPTZ NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE'
    CHECK (status IN (
      'ACTIVE','CONSUMED','EXPIRED','RELEASED'
    )),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (id, restaurant_id, table_id),
  FOREIGN KEY (claim_id, restaurant_id, table_id)
    REFERENCES inventory_claims(id, restaurant_id, table_id)
);

CREATE TABLE reservations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  booking_reference VARCHAR(32) NOT NULL UNIQUE,
  restaurant_id UUID NOT NULL,
  table_id UUID NOT NULL,
  user_id UUID NOT NULL REFERENCES users(id),
  hold_id UUID UNIQUE,
  claim_id UUID NOT NULL UNIQUE,
  party_size INTEGER NOT NULL CHECK (party_size > 0),
  starts_at TIMESTAMPTZ NOT NULL,
  ends_at TIMESTAMPTZ NOT NULL,
  status VARCHAR(24) NOT NULL
    CHECK (status IN (
      'PENDING_PAYMENT','CONFIRMED',
      'CHECKED_IN','SEATED','COMPLETED',
      'CANCELLED','EXPIRED','NO_SHOW'
    )),
  payment_mode VARCHAR(20) NOT NULL
    CHECK (payment_mode IN ('FREE','DEPOSIT')),
  deposit_amount_paise BIGINT NOT NULL DEFAULT 0,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  confirmed_at TIMESTAMPTZ,
  CHECK (ends_at > starts_at),
  CHECK (deposit_amount_paise >= 0),
  FOREIGN KEY (table_id, restaurant_id)
    REFERENCES restaurant_tables(id, restaurant_id),
  FOREIGN KEY (hold_id, restaurant_id, table_id)
    REFERENCES reservation_holds(id, restaurant_id, table_id),
  FOREIGN KEY (claim_id, restaurant_id, table_id)
    REFERENCES inventory_claims(id, restaurant_id, table_id)
);

CREATE INDEX reservations_by_restaurant_time
ON reservations (restaurant_id, starts_at);

CREATE INDEX holds_by_expiry
ON reservation_holds (expires_at)
WHERE status = 'ACTIVE';

CREATE INDEX claims_by_table_time
ON inventory_claims (table_id, starts_at, ends_at);



3.3 Critical database rules
This schema gives the booking engine a database-level exclusion constraint. However, SQL constraints alone are not the complete booking engine.

The application must also enforce the following invariants transactionally:
- A HELD claim must have exactly one corresponding active hold.
- A RESERVED claim must correspond to a reservation that still owns inventory.
- A BLOCKED claim must correspond to an authorized operational block.
- Expired holds must transition to RELEASED before another overlapping claim can be inserted.
- A confirmed reservation must retain its inventory claim.
- Restaurant capacity, ownership and reservation intervals must be validated before creating a claim.
- Reservations must copy the payment policy and price at checkout, so later restaurant policy changes do not alter existing transactions.
The starts_at and ends_at values in inventory_claims must represent the effective inventory interval, including any turnover buffer. Customer-visible reservation times remain separately recorded in reservations.

Additional production migrations should include composite foreign keys and consistency triggers for cross-table ownership, restaurant operating hours and policy validation where appropriate. Application services must be the only permitted writers to inventory-critical tables.
4. Atomic locking and concurrency control
The core booking operation is not simply checking whether a table is available. It is acquiring an exclusive inventory claim.
Transaction strategy

BEGIN;

-- Serialize inventory changes for this physical table.
SELECT id
FROM restaurant_tables
WHERE id = $1
  AND restaurant_id = $2
  AND operational_status = 'ACTIVE'
FOR UPDATE;

-- Capture authoritative transaction-time decision clock
-- after acquiring the table lock.
-- In the application, obtain clock_timestamp()
-- and pass that fixed value to subsequent statements.

-- Release expired holds for this table.
UPDATE inventory_claims c
SET state = 'RELEASED'
FROM reservation_holds h
WHERE h.claim_id = c.id
  AND c.table_id = $1
  AND c.state = 'HELD'
  AND h.status = 'ACTIVE'
  AND h.expires_at <= $3;

UPDATE reservation_holds h
SET status = 'EXPIRED'
FROM inventory_claims c
WHERE h.claim_id = c.id
  AND c.table_id = $1
  AND h.status = 'ACTIVE'
  AND h.expires_at <= $3;

-- Validate the requested interval, capacity,
-- policy and any remaining conflicts.
-- Then insert an exclusive claim.
INSERT INTO inventory_claims (
  restaurant_id, table_id,
  starts_at, ends_at, state, expires_at
)
VALUES ($2, $1, $4, $5, 'HELD', $6)
RETURNING id;

-- Insert reservation_holds using the returned claim ID.
-- Insert pending reservation and audit/outbox records
-- as required by the chosen booking workflow.

COMMIT;



The example is a transaction skeleton, not a standalone executable procedure. The implementation must check affected rows, validate all business rules and handle exclusion violations (SQLSTATE 23P01) as conflicts. The hold and claim changes must commit together.

For the final booking, the backend must acquire the same table lock, lock and verify the claim and hold, check expiry against the database clock, and atomically transition the claim from HELD to RESERVED.

5. Payments, webhooks and financial reconciliation
For the MVP, a restaurant can choose whether a booking requires a deposit. The customer does not independently override that policy.
Payment data model

CREATE TABLE payments (

Important payment engineering decisions
1. A Razorpay order is created outside the inventory transaction. Never hold a PostgreSQL row lock while waiting for an external payment API.
2. Webhooks must be signature-verified against the raw request body.
3. Duplicate gateway events must be processed idempotently.
4. The backend must verify the payment amount, order association, status and applicable capture state before finalizing a booking.
5. If the payment succeeds after the inventory claim expires, the booking enters reconciliation, not confirmation.
6. A refund request must have its own idempotent workflow and durable audit trail.
Financial edge case: A customer pays ₹200, but the server crashes before the booking is confirmed. Dine must recover the payment using persisted order identifiers and reconciliation jobs, then either complete a valid booking or initiate a refund.

For the initial version, a payment attempt must not silently extend the two-minute hold. A future version can introduce a controlled payment-processing lease, but it must be designed with an explicit expiry and gateway timeout policy.
